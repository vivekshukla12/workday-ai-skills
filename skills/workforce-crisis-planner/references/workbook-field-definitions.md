# Workbook sheet and field definitions

This reference records approved design decisions for the customer crisis-simulation intake workbook. Use it when explaining fields, assessing necessity, or revising the template. A field remains provisional until its sheet walkthrough is approved.

## Workbook-wide data-minimization and sensitivity standard

For every requested field, establish why the simulation needs it, whether the customer is reasonably expected to have it, and whether aggregated non-identifying data can support the same analysis.

Use this order of preference:

1. Aggregated, non-identifying data.
2. Anonymous data, only when re-identification is not reasonably possible.
3. Pseudonymous data when authorized record linkage is necessary. Treat it as personal data, not anonymous data.
4. Identifiable or sensitive data only when legally or operationally indispensable, with a documented purpose, approval, restricted access, and retention rule.

Every input column must be classified and visually identified as:

- **Required:** needed for the standard simulation.
- **Conditionally required:** needed only when the stated scenario or analysis is in scope.
- **Optional sensitive:** provide only when necessary and after the appropriate approval.
- **Calculated:** generated by the workbook or agent; the customer must not populate it.

Highly sensitive or commercially confidential fields must be optional by default, visibly highlighted in the input sheet, and accompanied by help text explaining when they are needed. Customers must leave them blank when the relevant scenario or analysis is outside the agreed scope.

Do not request employee names, personnel numbers, email addresses, raw health or absence details, protected characteristics, free-text personnel notes, credentials, Workday tenant names or URLs, or customer identifiers unless a later approved requirement explicitly establishes necessity and governance.

## Sheet 1 — Start Here

**Status:** Approved.

**Purpose:** Establish submission identity, time scope, calculation conventions, governance approvals, and calculated readiness without identifying the customer or Workday tenant.

| Field | Requirement | Approved definition |

## Sheet 2 — WD Workforce Extract

**Status:** Approved, except Off-site Capable FTE remains unresolved.

**Purpose:** Provide aggregated workforce supply using fields reasonably obtainable from Workday. Do not add non-Workday service assumptions to the extract.

**Row definition:** One aggregate workforce group for one period, entity when relevant, location, role, and Workday Worker Type. Multiple locations produce multiple rows. Never create one row per worker.

| Field | Requirement | Approved definition |
| --- | --- | --- |
| Row ID | Calculated | Generate automatically. |
| Period | Required | Month or week represented; Month is the default. |
| Entity Code | Conditional | Use for multi-entity scope or when entity differences affect the scenario. Permit a neutral code. |
| Location Code | Conditional | Support separate aggregate rows for relevant locations. Do not request addresses. |
| Role Code | Required | Use a governed Job Profile or Job Family mapping. Do not use Position ID or identifying business titles. |
| Worker Type | Required | Retain the Workday term and accept customer-configured values or an approved broader mapping. |
| Headcount | Required | Aggregate worker count. |
| FTE | Required | Aggregate full-time-equivalent capacity. |
| FTE on Leave | Conditional | FTE included in reported FTE but unavailable due to On Leave status on the reporting date. No leave type, dates, medical reason, or Worker ID. |
| Vacant FTE | Conditional | Approved position capacity currently unfilled, when reliable position data exists. |
| Off-site Capable FTE | Unresolved | Decide later whether it is reliably extractable or belongs in assumptions. |
| Scheduled Hours | Conditional extension | Exclude from the standard extract; add only for shift or short-duration hourly scenarios. |
| Total Base Pay | Optional sensitive | Aggregated amount only when role-level costing is necessary and Compensation access is approved. Never treat it as total employment cost. |
| Currency | Conditional | Include only when Total Base Pay is supplied. |
| Row Status | Remove | Final templates contain no sample rows; examples belong in help text. |

Apply a customer-approved minimum reporting-group threshold, preferably at least five workers. Suppress or combine smaller groups. Do not request names, Worker IDs, Position IDs, emails, protected characteristics, health details, absence reasons, performance or talent ratings, or personnel comments.

| Field | Requirement | Approved definition |

Do not add Service Code to the WD Workforce Extract. Relate workforce supply to service demand through Role Code and Location Code.

**Status:** Approved.

**Whole sheet:** Conditional. Complete only when supplier, customer, technology, site, utility, transport, regulatory, or related dependency scenarios are in scope.

**Row definition:** One dependency affecting one critical service and, where relevant, one location. Use multiple rows when one dependency supports several services.

| Field | Requirement | Approved definition |

## Scenario workflow and sheets

**Status:** Approved.

The AI agent should generate the majority of scenarios from validated input data, observed concentrations, capacity gaps, critical dependencies, and other evidence. Customer-submitted scenarios remain optional and allow the customer to request specific possibilities or strategic transformations.

The agent must present generated scenarios as proposals, not predictions or company facts. Customer review is required before detailed simulation and mitigation planning.

### Requested Scenarios

**Whole sheet:** Optional customer input.

**Purpose:** Let customers request a specific disruption, crisis, relocation, consolidation, expansion, closure, outsourcing, demand change, or other strategic workforce simulation without building the detailed scenario model themselves.

| Field | Requirement | Approved definition |
| --- | --- | --- |
| Request ID | Calculated | Stable identifier generated by the workbook or agent. |
| Scenario Request | Required when a request is entered | Plain-language event or transformation to evaluate. |
| Scenario Type | Required when a request is entered | Controlled category such as Disruption, Relocation, Consolidation, Expansion, Closure, Outsourcing, Demand Change, or Other. |
| Current Scope Type | Conditional | Entity, Location, Service, Role, or Dependency currently affected. |
| Current Scope Code | Conditional | Neutral code for the current scope. |
| Proposed Scope Type | Conditional | Target dimension for relocation or transformation scenarios. |
| Proposed Scope Code | Conditional | Neutral target code. |
| Effective Date | Conditional | Date the event or transition begins. |
| Transition Duration | Conditional | Expected implementation or parallel-operation duration. |
| Target Capacity % | Conditional | Intended capacity after the change. |
| Continuity Requirement | Conditional | Minimum service or capacity protected during transition. |
| Constraints | Optional | Outcomes or actions the agent must protect, avoid, or treat as out of scope. |
| Priority | Optional | Customer priority: Low, Moderate, High, or Critical. |
| Sensitivity | Required when a request is entered | Internal, Confidential, or Highly Confidential. Strategic location and restructuring scenarios should normally be treated as Highly Confidential. |

A request such as moving production from one anonymized location to another is supported. Analyze current and target workforce, skills, recruitment, knowledge transfer, parallel operations, cost, productivity, dependencies, and timeline at aggregate role-group level. Never recommend individual termination, retention, relocation, or selection decisions.

| Customer Comment | Yes | Optional | Concise explanation of an adjustment without personal or sensitive narrative. |

#### Assumption rules

Use assumptions in this priority order:

1. Validated customer data.
2. Customer-provided scenario assumptions.
3. Approved company planning assumptions.
4. Governed external reference data.
5. AI-generated assumptions as the last resort.

Never silently invent missing values or present an AI assumption as a customer fact. Prefer a range over unsupported precision. Every AI-generated assumption must identify the missing input, exact assumption, basis, confidence, result sensitivity, and information the customer can provide to improve the next run.

The customer may overwrite Current Value directly. Original Value and Original Origin remain protected. If Current Value differs from Original Value, Current Value Owner becomes Customer and Review Status becomes Customer Adjusted. Changing a value back must not erase evidence that it was reviewed where the platform can retain update metadata.

A portable workbook preserves the original value, current value, source, status, and simulation run. Complete cell-by-cell edit history requires platform version history or an application database and is not required in the portable first version.

Use clear visual markers for assumption origin and status. Highlight unapproved high-impact AI assumptions as warnings.

### Simulation iteration and result disclosure

Every execution receives a Simulation Run ID. Retain earlier runs for comparison rather than silently replacing them.

Every result must prominently disclose:

- AI-generated assumptions used;
- assumptions approved only for an indicative run;
- high-impact or low-confidence assumptions;
- excluded unapproved assumptions;
- information the customer can provide to replace AI assumptions; and
- changes in inputs, assumptions, and results since the previous run.

Baseline values should be derived from validated customer datasets where possible. Ask for a change amount or percentage instead of requesting the same baseline again.

## Control Totals

**Status:** Approved.

**Purpose:** Collect only the small number of independent source-system totals needed to reconcile submitted data. Customers do not populate technical validation results.

**Row definition:** One control total for one period or as-of date, domain, scope, and metric.

| Field | Customer edits? | Requirement | Approved definition |
| --- | --- | --- | --- |
| Check ID | No | Calculated | Generate automatically. |
| Period or As-of Date | Yes | Required | Use the applicable date basis for the controlled dataset. |
| Domain | Yes | Required | Controlled value identifying WD Workforce, WD Critical Skills & Credentials, Finance, Operations, Dependencies, or another approved dataset. |
| Scope Code | Yes | Conditional | Neutral entity or other approved scope code; permit ALL for a consolidated control. |
| Metric | Yes | Required | Controlled measure such as Headcount, FTE, Vacant FTE, FTE on Leave, Revenue, Labor Cost, or Capacity. |
| Source Control Total | Yes | Required for selected control | Total from an approved independent source-system report. |
| Workbook Total | No | Calculated | Total calculated from submitted rows using the same scope and date basis. |
| Variance | No | Calculated | Workbook Total minus Source Control Total. |
| Tolerance Override | Yes | Optional | Customer-approved exception to the default tolerance. |
| Status | No | Calculated | Pass, Fail, Warning, or Not Tested. |
| Control Reference | Yes | Optional | Neutral report or evidence reference; do not enter internal report names, URLs, tenant links, or access details. |
| Source Version | Limited | Dataset metadata | Prefer one dataset-level version rather than repetition per row. |
| Owner Role | Yes | Optional | Accountable role such as HR Data Owner; do not request a person's name or email. |
| Data Classification | Yes | Required | Internal, Confidential, or Highly Confidential. |

For WD Workforce Extract, use Headcount and FTE as the minimum recommended controls. Add Vacant FTE and FTE on Leave when supplied. Require skills, finance, and operational controls only for included metrics and where an independent approved control exists.

Exact financial control totals are Optional Sensitive. Missing optional controls create a disclosed limitation rather than an automatic conclusion that the data is incorrect.

## Validation Results

**Status:** Approved.

**Whole sheet:** Calculated and protected. Customers must not populate or edit it.

| Field | Approved definition |
| --- | --- |
| Check ID | Generated identifier. |
| Check Category | Structure, Completeness, Validity, Reconciliation, Privacy, Mapping, Approval, or Assumption. |
| Domain | Dataset checked. |
| Check Description | Plain-language explanation of the test. |
| Severity | Information, Warning, Indicative Only, or Blocking. |
| Result | Pass, Warning, Fail, or Not Tested. |
| Affected Row Count | Count of affected aggregate rows without reproducing sensitive records. |
| Resolution Guidance | Specific correction or additional information needed. |
| Simulation Impact | Final allowed, Indicative only, or Blocked. |
| Run ID | Validation or simulation run identifier. |
| Checked At | Execution timestamp where supported. |

### Required automatic validations

Test structure, required-field completeness, aggregate-row uniqueness, valid codes and mappings, date and unit validity, non-negative measures where appropriate, currency presence, version separation, approval gates, privacy thresholds, and reconciliation.

Also test that:

- FTE on Leave does not exceed FTE.
- Minimum FTE and other business requirements have approval.
- Shared capacity is not double-counted.
- AI assumptions are visibly identified.
- Unapproved assumptions are excluded from final simulations.
- Optional sensitive values are not treated as required when their scenario is outside scope.
- Exact sensitive data is used only when its purpose and approval are recorded.

### Failure behavior

- **Warning:** Continue and disclose the limitation.
- **Indicative Only:** Permit an explicitly labelled indicative simulation but prohibit final conclusions.
- **Blocking:** Stop simulation until corrected or approved.
- **Not Tested:** Disclose that validation evidence is unavailable.

Blocking examples include impossible workforce values, unmapped required codes, incompatible units, missing required approvals, or a final result that depends on an unapproved AI assumption. Missing optional financial data, banded dependency estimates, or unavailable independent controls normally produce warnings or indicative-only limitations rather than blocking unrelated scenarios.
